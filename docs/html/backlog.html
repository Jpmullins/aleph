The product thesis — plugins A

This is the largest gap. CLAUDE.md opens with “an agent that authors plugins for itself and activates or deactivates them as needed… The kernel is the product.” Almost none of it exists.

A1

Plugin system

Not built

Asked“Everything is a plugin”, from deepseek-harness and cordis — compiling and communicating efficiently enough to feel like one system.

Existsaleph-kernel has effects, capabilities, a boot manifest, an AST gate, skills, a spawn ledger. Ten capabilities mount at boot.

MissingNo Plugin type, registry, activate/deactivate, lifecycle, dependency resolution or isolation boundary. A plugin today is a workspace package wired in by hand. Nothing can be added or removed at runtime.

A2

The agent authors its own plugins

Not built

AskedThe agent writes plugins for itself, with guardrails preventing it from removing load-bearing capability.

MissingEntirely — no authoring path, no guardrail, no blast-radius check against removal. The kernel already computes blast radius for effects, which is the primitive this builds on.

A3

Per-plugin A2UI catalogs

Not built

Asked“Every plugin can come with its own catalog for A2UI and publish it.”

ExistsExactly one catalog — and a CI sweep that enforces there is only one.

MissingCatalog composition. The sweep’s invariant has to change from “one catalog” to “one per plugin, merged without id collisions”, and the generator has to merge rather than copy.

A4

Per-plugin settings cards

Not built

Asked“Every plugin can have a fully scoped settings card”, with three tiers by trust level.

ExistsOne hand-written SettingsBody covering model profile and connectors.

MissingA settings contract a plugin declares, a renderer that composes declared cards, and the trust tiering.

Settings and configuration B

B1

Settings is a drawer, not part of the workbench

Not built

ExistsDrawers.tsx renders settings in a slide-over. The pane registry serves seven panes and settings is not one of them.

MissingSettings as a pane, so it obeys the same model as everything else — and so per-plugin cards have somewhere to land.

B2

The model endpoint cannot be set

Not built

AskedRepeatedly: Aleph serves no models, it connects out to any OpenAI-compatible endpoint — litellm, ollama, vllm, bedrock — and the endpoint must be settable, not baked in.

Existslitellm_base_url read once from env. Discovery reads whatever that gateway serves; the picker lists those models.

MissingAny way to change it without editing .env and restarting. No route, no UI field, no per-project override, no credential store, no “test this endpoint” probe before saving. This is what blocks using Aleph against anything but the currently configured gateway.

B3

Saving a model binding returned 500

Fixed

updated_at has a server-side onupdate, so the flush leaves it expired; reading it lazy-loads and raises MissingGreenlet. Two of the three write paths already called session.refresh — one even documents why. The PATCH handler was missed.

B4

Every server error surfaced as a CORS failure

Fixed

add_middleware prepends, so CORS added first became innermost — inside the error and auth middleware. Any response those produced reached the browser with no Access-Control-Allow-Origin, so the console blamed CORS and the real status was never seen. The 500 above arrived as “blocked by CORS policy”.

C1

CopilotKit Enterprise Intelligence

Misjudged — still decline

CorrectionMy first read covered threads, inspection and multi-tenancy and concluded Aleph had equivalents. It missed the self-improvement pillar entirely — in-context learning from human feedback with no fine-tuning, captured clicks and edits and approval signals, learning containers per user or org, and “users show the agent a task once, it learns the skill”. That is the thing worth wanting, and it was right to keep asking.

BlockerCloud-hosted sends every interaction to CopilotKit. Self-hosting is a Helm chart into Kubernetes. Aleph deploys with docker compose, which was explicit.

VerdictStill decline, for a better reason: Deep Agents provides these primitives natively and Aleph already runs it (0.6.6, skills wired). See H — agent-authored skills, durable skill storage, and iterate-until-good grading, with no license, no Kubernetes, and nothing leaving the deployment.

C2

MCP Apps

Not built

The third band. Would let an MCP server ship its own UI — close to what A3 needs for plugins.

C3

An agent Inspector pane

Not built

The one genuinely valuable idea from Enterprise Intelligence, rebuilt on data Aleph already has: the AG-UI event stream, tool calls with arguments and results, run status, and the failure point when a run errors. A pane, not a hosted console — and the reason E1 is still untraced is that nothing like it exists.

Known broken, carried in CLAUDE.md D

These predate this session and are still true.

  • D1 · commit_revision is not atomic on the path agents use. It row-locks only when given a page_id; the by-title path computes revision_no as max+1 on an unlocked page.
  • D2 · Cost attribution has a hole. A ChatOpenAI response without usage is silently uncosted.
  • D3 · The runtime bridge drops the caller’s credential. oidc mode cannot authenticate the chat path. local — the only deployed mode — is unaffected.
  • D4 · SSE cannot carry a bearer token. EventSource sets no header. Parked until OIDC deployment is taken up as a whole.

Observed in the running stack E

From a live browser console and the API logs. Not yet diagnosed unless noted.

  • E1 · The agent run fails, then the runtime keeps streaming. Cannot send event type 'TOOL_CALL_START': the run has already errored. That is the symptom; the primary RUN_ERROR is untraced.
  • E2 · POST /scholar/search returns 503 repeatedly.
  • E3 · Compiled page HTML is broken in the reader. The sandboxed iframe blocks scripts and the page preloads a font that 404s and is CORS-blocked from the null origin, so it renders unstyled.
  • E4 · Agent model calls cannot be priced. claude-sonnet-4-6 records pricing_source=unknown — correct behaviour, never a silent $0, but agent spend is unpriced in practice.
  • E5 · Gateway rate limiting. Not yet characterised; the subagent fan-out is the likely cause.
  • E6 · Lit dev-mode warning from a CopilotKit dependency. Cosmetic.

Done, for an honest baseline F

So the list above reads as what remains, not as everything.

  • Corpus-wide hybrid retrieval, measured: recall@1 0.91 hybrid against 0.60 lexical

  • Gateway-driven model discovery, autoconfigure by requirements, pricing provenance

  • Five CI sweeps, including surface-binding and pane-registry agreement

Deep Agents capabilities Aleph is not using H

Aleph runs deepagents 0.6.6. The newer releases carry most of what the self-improvement thesis needs, and almost none of it is wired. Skills are live — four bundled SKILL.md skills following the Agent Skills spec. What follows is what is not.

Adoption table

Aleph’s agent runs in-process inside FastAPI, so the sync/async column is not a preference — anything on the request path must be async or it blocks the event loop. Beta and preview are marked so the risk is explicit, not so the item is skipped.

H6’s ASGI transport is the detail that makes async subagents viable here. With url omitted the SDK routes through in-process function calls instead of HTTP — no network hop, no extra auth — which fits Aleph’s in-process agent exactly. Local runs need the worker pool raised: a supervisor with three concurrent subagents needs four slots, and under-provisioning silently queues launches rather than failing.

H1

The agent cannot write a skill

Not built

This is the self-improvement mechanism — the docs say it plainly: “ask your agent to write a skill for a task you worked on”. Aleph’s skills backend is a read-only filesystem, so the agent reads skills and can never author one. Nothing it learns survives the session. StoreBackend is the durable answer.

H2

aleph_kernel.skills is dead code

Broken

Two skills implementations exist. The one that runs is deepagents’. The other — AST-gated before execution, exec’d into a fresh namespace, loadable as a capability with a lifecycle — has no callers outside its own tests. Verified.

The dominant defect class in this codebase, and it matters more than most: its AST gate is exactly the admission control an agent-authored skill needs, and its lifecycle is what activate/deactivate would build on. Wire it or delete it — leaving it reads as “covered” and is not.

H3

RubricMiddleware

Not built

Declare what “done” looks like; the agent self-evaluates and revises until it passes or hits a cap. Needs ≥0.6.5 — available today. The wiki lint’s 16 named criteria are already rubric-shaped.

H4

HarnessProfile — per-model tuning

Not built

Prompt tweaks, tool-description overrides, excluded tools and middleware, per provider or model, from YAML. Aleph is meant to run against any endpoint and sends one prompt and one tool set to every model. A 7B local model and Opus do not want the same harness. Pairs with B2 rather than following it.

H5

Interpreters and dynamic subagents

Not built

Fan-out from code — loops, retries, parallel batches — with intermediate results kept out of model context. Likely the fix for E5: today the model decides how many subagent calls to issue one turn at a time, which is what makes request volume unpredictable.

H6

Async subagents

Not built

Background tasks returning a job id immediately, with check, mid-flight update and cancel. Aleph’s research loop is exactly this shape and blocks today.

H7

stream.subagents

Not built — and it is what C3 needs

One stream handle per delegated task, each with .messages, .tool_calls, .values and .output, labelled by subagent name. That is the Inspector’s data model, already in the library — C3 does not need building from raw AG-UI events.

H8

OpenWiki and the Open Knowledge Format

Check

LangChain ships OpenWiki — a CLI maintaining a Markdown wiki as durable agent context, built on Deep Agents — emitting OKF v0.1: front matter, indexes, linked concepts. Aleph’s wiki schema converged on the same shape independently. If OKF becomes a real interchange format, aligning now is cheap and later is not.

Suggested order

A real sequence — each step is the forcing function for the next.

  1. The model endpoint, and per-model harness profiles B2 + H4One piece of work. Pointing Aleph at any endpoint is half useful while every model gets the same prompt and tool set.
  2. The agent can write a skill H1 + H2 + A2The self-improvement mechanism. A writable store so an authored skill survives the session, the kernel’s AST gate as admission control, and the blast-radius check that stops it removing load-bearing capability. Not a system from scratch.
  3. The Inspector H7 + C3stream.subagents is the data model, already in the library. Build it before chasing E1.
  4. Trace the RUN_ERROR E1With the Inspector in hand.
  5. Settings as panes, per-plugin cards, and the four UI rebuilds B1 + A4 + GDrawers.tsx is all three problems in one file.
  6. Interpreters and dynamic subagents H5Also the likely fix for E5 — model-driven fan-out is what makes request volume unpredictable.
  7. Rubric grading H3The wiki lint already gives a concrete first rubric to write.
  8. The remaining UI revisions GPlus a sweep so the drift cannot return.
  9. Catalog composition, then the plugin system A3 → A1A1 last on purpose: items 2, 5 and 6 are the forcing functions for its shape. Designed first, it would be designed against guesses.
  10. Async subagents, the OKF read, then the rest H6, H8, E2–E4, D1–D2Not doing C1 — Deep Agents gives the same primitives with no license and no Kubernetes. D3/D4 parked until OIDC.
